Hypergeometric

Switch your AI agent to a new model — and prove nothing broke

What the system does and how it flows, in plain words.

The problem, in one minute

An AI agent runs on two things: a model, and a set of written instructions — the system prompt, the tool descriptions, the skills. The instructions were written by hand, tuned to whatever model was current at the time, and then left alone. Meanwhile new, better, cheaper models come out every month.

When you swap the model, three things happen quietly: some instructions keep working, some get ignored by the new model, and some turn out to have never been needed at all. Nobody can tell which is which by reading. So teams either stay on the old model and overpay, or switch and hope.

The standard advice — “run your test suite” — assumes a test suite. Most agents in production don’t have one, and building one takes months.

The key idea

Every instruction already says what correct behavior looks like. “Always answer in JSON” — the answer is JSON or it isn’t. “Never export data without a filter” — the filter is there or it isn’t. “Keep answers under 150 words” — count the words.

So nobody has to write tests. The instructions are the tests. The system reads each rule and generates the checks for it automatically.

The flow

1 — Split. The instructions are broken into single rules — “always answer in JSON”, “never export without a filter” — each one small enough to test, fix, and explain on its own.

2 — Test. For each rule, the system generates hundreds of varied scenarios: simple direct asks, long messy conversations, pushy users arguing against the rule. Each scenario runs four ways — with the rule in and with it taken out, on the old model and on the new one. Same scenarios everywhere, so the comparison is fair. Then it counts how often each model followed the rule.

3 — Verdict. Two questions decide each rule’s fate on the new model:

Follows the rule when it’s there? …and when it’s taken out? Verdict
Yes Yes — behaves the same without it DELETE  the model does this naturally; the rule is dead weight
Yes No — breaks without it KEEP  the rule is doing real work
No No REWRITE  the model ignores this phrasing

4 — Fix. For each broken rule, the system writes many alternative phrasings — different wording, different placement (maybe the rule belongs in the tool’s own description, not the prompt), checklist instead of prose. It runs the best candidates against the hardest scenarios and keeps what the new model actually obeys — never what merely reads well. The winner is re-tested on the full scenario set, and at the end the whole rebuilt config gets one more pass together, because rules can interact.

5 — Certify. Out come three things: the ported config, a migration report where every claim is a count (“followed 97 times out of 100”), and a change ledger — every edit with its before/after numbers.

A tiny example

Numbers are “times followed, out of 100 scenarios”, with the rule present:

RuleOld modelNew modelVerdict
“Always answer in JSON” 98 99 (96 even without the rule) DELETE
“Never export without a filter” 97 71 REWRITE
“Say so when data is missing” 93 95 KEEP

The export rule regressed on the new model. After rewriting it as a short checklist inside the tool’s own description, it re-tested at 96 out of 100 — and that before/after pair goes into the ledger as proof.

One more trick: catching habits nobody wrote down. Old models often do good things no instruction asks for — always showing units in tables, for example. The system watches the old agent’s real traffic, spots these reliable habits, and writes them down as new rules before the switch. Otherwise they vanish silently with the old model, and no test would ever notice.

Why the numbers can be trusted

  • Enough scenarios per rule that a badly broken rule cannot slip through by luck.
  • Both models see exactly the same scenarios — differences are real, not sampling noise.
  • Every rate ships with a confidence range, and borderline rules get more samples instead of a coin-flip verdict.
  • Nothing is ever changed because the text “looks wrong” — only measured behavior can delete or rewrite a rule.

Where it stands

The design is complete. Next step is a weekend-sized proof on a real agent config — tens of dollars of API calls with clear go/no-go gates — then an automated version that produces the read-only migration report.
